# 设计说明

**这份文件回答「为什么」，不回答「怎么用」。** 怎么用看 [`README.md`](README.md)，
跑出来的数字看 [`../FINDINGS.md`](../FINDINGS.md)。

每一条约束下面都跟着一次实测或一次踩坑 —— 它们不是审美偏好，是撞出来的。

## 设计架构

### 一、分层：库不认识 PII，也不认识你的业务

```
应用
 │
 ├─ 意图路由                        决定这个问题走哪条路
 │    ├ 个人数据 / 结构化查询  →  工具调用 + 授权检查   → 缓存 plan
 │    └ 学科内容问答          →  RAG                  → 缓存 answer
 │
 ├─ PII 层                          检测 · 脱敏 · 还原 · 能否跨主体共享
 │    └ 产出两份文本：matchText（脱敏后）+ retrievalText（保留实体）
 │
 └─ @jolli.ai/semantic-cache
      不认识 PII · 不实现检索 · 不实现存储 · 不调用 LLM
      只回答一个问题：这次该不该复用，复用哪一条
```

个人数据不进可检索语料，是**路由层**的事；脱敏与还原是 **PII 层**的事。
库只守一条边界：声明为已脱敏的请求，不允许把 **answer** 条目放进共享 scope。

### 二、什么由你提供，什么库内固定

```
                你提供                        库内固定，不给选
  ──────────────────────────────────────────────────────────────────
  打分   RecallStage                     ⑥ 的算子固定为 top-1
         RerankStage（可选）              阈值必须跟打分器一起给
         SupportStage
  存储   CacheStore                      scope + 未过期 的 pre-filter
         （内存 / pgvector 两个现成实现）
  检索   Retriever                       —
  策略   CachePolicy（可选）              noStore ⇒ 拿不到写入票据
  隔离   ScopeResolver                   org 必填；scope 由库转义拼接
                                         脱敏 × 共享 × answer ⇒ 抛错
  版本   SourceVersionResolver           按引用资料比对，非相似度
  生成   Generate / Refine（可选）        何时调用由库决定
  向量   ——（一律库内计算）                答案用 passage 侧编码
```

**向量不由调用方传**，是为了堵死跨向量空间比较：答案必须用检索模型的 passage 侧
编码，才能和检索片段比。用句对模型编码答案、用检索模型编码片段，余弦没有意义。

### 三、读路径：六道闸与两种载荷

```
  resolve(prompt, generate)
        │
   ①  scope 门控          ← ScopeResolver（你的隔离策略）
        │                   redacted × shared × answer ⇒ 抛错
        ▼
   ②  精确匹配 ─── hit ──────────────┐
        │ miss                       │
        ▼                            │
   ③  向量召回 top-k                  │   无候选 / top-1 < recall.floor ─→ 生成
        │ pass                       │
        ▼                            │
   ④  精排（有 RerankStage 才存在）    │   < rerank.floor ─────────→ 生成
        │ pass                       │
        └──────────┬─────────────────┘
                   ▼
            kind == "plan" ? ── 是 ──→ 返回计划（⑤⑥ 不适用）
                   │ 否                 实体是参数，执行时填参 + 授权
                   ▼
   ⑤  资料版本比对          版本不符 ── evict ──→ 生成
        │ 一致
        ▼
   ⑥  回答校验（对 top-1）   < support.low ── evict ──→ 生成
        │
        ▼
     支撑度 ≥ support.high ? ── 是 ──→ 复用
                            └─ 否 ──→ 微调（有 Refine）/ 否则生成
```

**② 命中也要过 ⑤⑥**：缓存键建在脱敏文本上时，占位符塌陷对精确匹配同样成立。

**⑤⑥ 的分数无论开关都会算出来**，关掉时 trace 标 `would-exit` —— 一次运行就能
看出"关掉会怎样"，不用重跑。

### 四、三个打分器角色与阈值绑定

```
  角色       比什么                  尺度            阈值
  ─────────────────────────────────────────────────────────────────
  recall     问题 ↔ 缓存里的问题      句对模型的余弦    floor
  rerank?    问题 ↔ 缓存里的问题      该重排器自己的     floor + target
             或   ↔ 缓存里的答案      （两者尺度不同）
  support    答案 ↔ top-1 检索片段    检索模型 passage  high / low
```

三个尺度**互不可换**。所以阈值不是一个独立的 `thresholds` 配置块，而是和打分器
捆在一个 `Calibrated<Scorer, Thresholds>` 里，还带一个必填的 `calibratedOn` —— 
换打分器就拿不到旧阈值，也留下了这组阈值是在什么数据上标的。

**没有 `RerankStage` 就是没有 ④ 这道闸**，不会退化成"拿它的闸值去卡召回余弦"。
那条退化路径正是尺度混用的来源，已经删掉；想在无精排时收紧问题侧，
调 `recall.thresholds.floor`。

**`recall.floor` 卡的是 top-1，不是每条候选。** 它回答的是「这批候选值不值得看」——
top-1 都不到线就没必要往下走。所以配了 ④ 之后，**精排可以选中一条余弦远低于
`floor` 的候选**，那是设计使然（④ 的作用就是推翻 ③ 的名次；FINDINGS 里那条
「任务错配的重排器净负」说的正是这个权力有多大）。想让 `floor` 成为硬门槛，
现在得在 ④ 之外自己拦。

这个取舍必须看得见，所以 ④ 的 trace 除了精排分还报**胜出者自己的 ③ 余弦**，
低于 `floor` 时额外标出来 —— 否则「被复用的那条 ③ 只有 0.3」这件事在哪儿都查不到。

## 为什么不是「加个向量库 + 一个阈值」

单一余弦阈值管不了三类不同的失效，因为它们需要的证据类型不同：

| 失效 | 例子 | 需要的证据 | 由谁管 |
|---|---|---|---|
| 意图之差 | 「什么是过拟合」vs「什么是欠拟合」 | 更强的语义判别力 | ④ 精排 —— **前提是模型任务匹配**，见文末 |
| 资料改版 | 老师改了大纲，旧答案引的是上一版 | 版本事实（可直接查） | ⑤ 版本比对 |
| 实体塌陷 · 同词不同指 | 「Hinton 提出了什么」vs「LeCun 提出了什么」；「归一化」在两章各指一事 | 问题侧看不出，但检索结果不同 | ⑥ 回答校验 |

指望一个阈值同时管住三件事，只能得到一个既漏又误的中间值。

### 和主流语义缓存的功能对照

上面那段是抽象理由，这里是具体的：主流方案缺的到底是哪几样，以及这个库缺主流的哪几样。

| | GPTCache（开源） | Redis LangCache（托管，preview） | 本库 |
|---|---|---|---|
| 相似度召回 + 阈值 | ✅ 默认 `similarity_threshold=0.8` | ✅ 可配距离阈值 | ✅ ③，阈值必须自己标 |
| 精排（cross-encoder 二次判定） | 有「model-based similarity」可选 | ✅ 有微调过的 reranker | ✅ ④，且形态（问↔问／问↔答）是显式选择 |
| **资料版本比对** | ❌ | ❌ | ✅ ⑤ |
| **答案是否仍被检索片段支撑** | ❌ | ❌ | ✅ ⑥，算子固定 top-1 |
| 多租户 / scope 隔离 | ❌ | ✅ users / apps / sessions + 自定义 attributes | ✅ ① `ScopeResolver` |
| PII 边界 | ❌ | ❌ | 声明式：脱敏 × 共享 scope × answer **直接抛错** |
| 缓存计划（plan）而非答案 | ❌ | ❌ | ✅ 两种载荷，⑤⑥ 对 plan 自动不适用 |
| 阈值与打分器绑定、标定语境必填 | ❌ 阈值是独立配置项 | ❌ | ✅ `Calibrated<Scorer, Thresholds>` + `calibratedOn` |
| 按请求决定「这条走不走缓存」 | ✅ `cache_enable_func`（布尔，管读+写）、`cache_skip`（只管读） | ❌ 无钩子 —— REST 是显式两步，不想缓存就别调 store | ✅ `CachePolicy`：`noCache` / `noStore` 正交 + 每条 TTL，**理由必填** |
| 判定不缓存时能否**保证**写不进去 | ❌ 只是不执行写入分支 | ❌ | ✅ `noStore` ⇒ `prepareWrite()` 抛，`prepareTicket()` 也抛 |
| 按请求调相似度阈值 | ✅ `cache_factor` 乘在阈值上 | ❌ | ❌ 阈值绑在构造期的 `Calibrated<>` 上 |
| 自动生成标定探针 | ❌ | ❌ | ✅ `generateProbes()`：从上传的资料构造按难度分档的探针 |
| LLM adapter（OpenAI 等 API 兼容） | ✅ | ✅ REST API | ❌ 生成由调用方传入 |
| 向量库适配 | ✅ 九种（Milvus/FAISS/Chroma/Qdrant…） | 托管 | 三种（内存 / pgvector / Redis vectorset） |
| 淘汰策略 | ✅ LRU / FIFO / LFU / RR | ✅ 自动淘汰 | ✅ 同样四种，三个后端语义一致；**容量按 scope 计**，默认 `fifo`（`lru`/`lfu` 要在命中路径上多一次写） |
| 多模态（图像） | ✅ | ❌ | ❌ |
| 内置指标看板 | ❌ | ✅ | ✅ `Metrics.ts`，LangCache 同款那组 + `missedAtGate` / `evictions`；**刻意不算正命中率**（需要标签） |

**定位差别比功能差别更要紧。**GPTCache 与 LangCache 假设的是**纯 query→response 缓存**：
问题像不像，是唯一要判断的事。本库假设的是**RAG 之上的缓存**，于是多出两类失效 ——
资料改版了（⑤）、旧答案已经不被现在会检出的片段支撑了（⑥）。那两道闸不是「更严一点」，
是在问一个前两者结构上问不出的问题：**答案和它的依据之间的关系还成不成立。**

所以这张表不该读成「本库功能更多」。反过来看更准确：**它是精度层，不是基础设施层。**
LLM adapter、九种向量库、多模态 —— 那些是要接进生产必须有的东西，这里没有，而且不打算有
（`CacheStore` / `Retriever` / `Generate` 都是让你把已有的接进来）。
真要上生产，把这一层套在 GPTCache 或 LangCache 之上比替换它们更合理。

**「该不该缓存」这一格,三家的形态差别比有无更值得看。**读源码核过：

- **GPTCache** `Cache.init(cache_enable_func=cache_all)`，每次请求拿**原始调用参数**判，
  返回布尔。它挡在 embedding 之前（`adapter.py:77`），所以编码开销也省得掉 ——
  和这里把 `CachePolicy` 放在闸 ① 之前是同一个位置。另有 `cache_skip` 只关读、
  `cache_factor` 按次乘在阈值上。**还有一手很聪明的**：`temperature` 自动驱动跳过
  （`<=0` 用缓存，`>=2` 一律跳过，中间按 softmax 概率跳）—— 高 temperature 意味着
  调用方明确要多样性，复用旧答案本身就违背意图。这是个 API 语义天然给出的信号，
  不用猜也不用配。
- **LangChain** `BaseCache` 只有 `lookup/update/clear`，**没有任何钩子**；控制粒度到
  模型实例（`llm.cache`），到不了单次请求。
- **litellm** 是四层粒度（调用类型 / 全局 `default_on|default_off` / 单次请求 / virtual key），
  借的是 HTTP `Cache-Control` 语义：`no-cache` 关读、`no-store` 关写、`s-maxage` 定 TTL。
  代价是有一批**配不了的隐式策略**：提不出 prompt 的调用（embedding / rerank /
  transcription）直接静默 no-op —— 你以为开了，那部分流量根本没走缓存，日志里也看不出。

所以这里的 `noCache` / `noStore` 是**照抄 litellm 的 HTTP 语义**，不是自造词：那套词汇
每个工程师都已经懂，而且天生分读写两侧 —— 一个布尔表达不了「重新回答」（只关读、
仍要写回）和「出五道练习题」（只关写、照常读）这两种。

真正只有这里有的是**保证**：三家的「不缓存」都是"调用方自觉"，`cache_enable=False`
只是不执行写入分支，没有任何东西阻止你绕过 adapter 直接调 `data_manager.save`。
这里 `noStore` 生效时 `prepareWrite()` 和 `prepareTicket()` 都抛 —— 写不进去，
不是不去写。

同一张尺子上的实测数字见 [`FINDINGS.md`](../FINDINGS.md) 的「和主流基线的同尺度对比」。



## API 里固化的教训

这些不是风格选择，是实测踩出来的，所以做成了类型层面绕不过去的形状。

### 1. `matchText` 和 `retrievalText` 是两个必填字段

上游做了 PII 匿名化时，缓存键必须建在匿名化后的文本上，而**检索必须用保留实体的原文**。
两者混用时，回答校验对实体塌陷完全失明 —— 两个不同的人检出同一批片段，这一层就废了。

实测：把检索换成匿名化后的文本，13 条用例里多漏 2 条，**精确就是两条实体塌陷**，
其余 11 条判定完全不变。是选择性失效，不是整体失效。

没有匿名化的应用把两者传成同一个字符串即可。

### 1.5 PII 过滤在 SDK 之上，但边界由 SDK 守

库不认识 PII —— 检测引擎（Presidio / Comprehend / 正则）和合规要求各家不同，
不该由缓存库来理解。**分层是：应用 → PII 层（检测/脱敏/还原）→ 本 SDK。**

但这个分层有个构造上必然的陷阱，SDK 必须堵死：

脱敏之后，「张三的作业二扣了多少」和「李四的作业二扣了多少」变成**同一个字符串**。
它们塌成同一个缓存键，而答案里带着 `<PERSON_1>` 占位符 —— 跨主体复用时用当前请求
的实体映射去还原，就会把甲的答案安上乙的名字。这不是概率问题，是必然。

所以契约是两条：

```ts
await cache.resolve({
  matchText: redactedText,      // 脱敏后 —— 缓存键建在它上面
  retrievalText: originalText,  // 保留实体的原文 —— 检索必须用它
  redacted: true,               // 如实声明
  context: { userId },
}, generate);

// ScopeResolver 必须为脱敏请求返回隔离 scope
scope: prompt => prompt.redacted
  ? { key: `user:${prompt.context.userId}`, shared: false }
  : { key: `course:${prompt.context.courseId}`, shared: true },
```

`redacted: true` 落进 `shared: true` 的 scope，SDK **直接抛错**。只返回字符串的
ScopeResolver 会被保守地当作共享 scope。

**还原（de-anonymization）一律在 SDK 之上做，而且只对本主体的条目做。**
库返回的 `answer` 是原样存的文本；跨主体还原从来都不安全，隔离 scope 就是为此。

一句话：声明是第一道防线，⑥ 回答校验是**声明缺失时**的兜底 —— 现实中最常见的
失误就是上层忘了声明。两道都要有。

### 1.8 支撑度用 top-1，且标定与实现必须同算子

「旧答案是否仍被检索片段支撑」要落成具体算子，三种写法差别巨大：

| 算子 | 语义 | 失效方式 |
|---|---|---|
| 对 top-k 取重心 | 和这批片段整体像不像 | 片段少时无关的也被捞进来，平均后信号稀释 |
| 对 top-k 取 max | 有某个片段撑得住旧答案 | **旧答案自己的来源片段常常还在 top-k 里**，跟自己比当然高分 |
| 对 **top-1** 比 | 旧答案和现在会据以回答的那篇一不一致 | 选用 |

取 max 那次很具体：问「Breiman 提出了什么方法」，检索回来的三篇里仍含 Vapnik 那篇，
而缓存答案正是从它生成的，支撑度被自己的来源顶到高位，塌陷放行。

**更隐蔽的是它让标定失效。**标定拿「答案 ↔ 单篇文档」比、实现却取 top-k 的 max，
两者不是同一个算子，标出来的阈值根本不适用 —— 而后果不是报错，是把实现缺陷
当成机制的固有边界写进结论。库内固定为 top-1，就是不让调用方在这里做选择。

**代价写在明处：top-1 把这道闸的判定绑在了检索层的排序上。** 所以 `Retriever` 的契约
要求返回值按相关性降序 —— 顺序错了，这道闸测的就不是「旧答案和现在会据以回答的那篇
一不一致」，而阈值仍然照常算得出来，不报错。更麻烦的一面见「诚实的边界」最后一条：
top-1 抖动会直接翻转判定，而 ⑥ 判负是**破坏性**的。

### 1.9 替换一条缓存：先写新的，写成了才删旧的

中带（支撑度落在 low 与 high 之间）要么微调后写回、要么重新生成后替换。先前两条路都是
**先 `evict` 再生成**，看着更直觉，实际是把「替换」变成了「先删掉，然后试着写一条」：

| 中途出什么事 | 先删后写 | 先写后删 |
|---|---|---|
| 生成抛错（LLM 超时、限流） | 旧条目已经没了，什么也没换上 | 旧条目还在 |
| 产物没有资料依据（检索故障） | 同上 —— 净丢一条 | 旧条目还在 |
| 写入抛错（存储故障） | 同上 | 旧条目还在 |

实测过第一种：一次生成失败净丢一条本来还能用的缓存。这和 ⑥ 那条「判不了 ≠ 判定为无效」
是同一条不变式的三个部分 —— **一次故障不改变缓存状态**：⑥ 缺证据时不驱逐、
没有依据的答案不写入、替换先写后删。三处缺一处，那条不变式就是空话。

代价是同 (scope, matchHash) 的两条会共存几毫秒。这是安全的，因为 `getByHash` 的契约
就是取最新的那条 —— 而那条契约本来就是为并发写入定的。

### 2. 三个模型角色分开，不能共用

```ts
interface PairEncoder      { embedQuestions(t) }              // 问题↔问题（对称）
interface RetrievalEncoder { embedQuery(t); embedPassage(t) } // 问题↔段落（非对称）
interface Reranker         { score(query, candidate) }        // 精排
```

实测两次任务错配，**都不报错**：

- 拿句对模型（`paraphrase-*`）做检索：「什么是过拟合？」top-1 是**批归一化**（0.366）；
  换成检索训练的模型后是「过拟合」（0.888），top-1 命中 7/7。
- 拿段落重排器（`ms-marco`）比问题↔问题：中文上四组难度递减的输入全部落在
  0.9975–0.9988，**跨度 0.0013**。

两次都是模型正常加载、返回合法的 0~1 分数、程序跑完。你会拿着这些数去标定阈值 ——
而标定一个常数，标出来的阈值当然也没有意义。

**`candidate` 传什么是 `RerankStage.thresholds.target` 上的一个必填选择**，因为它决定
分数尺度。传缓存里的旧**问题**（`"question"`）需要句对训练的模型；传旧**答案**
（`"answer"`）就正好是 query→passage，段落重排器适用 —— 后者语义上也更直接：
「这条缓存的答案，回答得了我这个问题吗？」

这一格先前只写在注释里、实现写死传旧问题，于是上面那些 ④ 的数全是问↔问形态量的，
而唯一可得的 `bge-reranker-base` 恰恰是 query→passage 训练的。补上之后（18 对中文对子）：

| 形态 | 留一交叉验证 | 训练误差 | 假负 | 假正 |
|---|---|---|---|---|
| `"question"` | 50.0%（等于抛硬币） | 6/18 | 1 | 5 |
| `"answer"` | **27.8%** | 4/18 | **0** | 4 |

**假负归零是关键**，因为「④ 开着还砍掉 2 次合法复用」的负收益说的就是假负。

训练误差那一列的阈值是在同一份数据上选的，偏乐观；留一那一列才是泛化估计。
**形态之间的比较（配对比较）比任一个 θq 的绝对值稳健得多** —— 后者这份数据定不出来：
平台宽 0.62、bootstrap 95% 区间 0.287~0.999。所以这张表支持的结论是「形态选 `"answer"`」，
**不是**「floor 用 0.35」。floor 必须在你自己的数据上标，量化过程见 FINDINGS 那一节。
反过来，把 NLI 模型从 `"question"` 换到 `"answer"` 会直接塌掉（假负 5/9）——
**换形态和换模型一样是任务错配的来源**，所以 `target` 和 `floor` 捆在同一个对象里，
换形态就拿不到旧的 θq。

**`target: "answer"` 下 plan 条目没有可比的 candidate**（它们的 `answer` 是空串），
这道闸对它们标 `off` —— 和 ⑤⑥ 对 plan 不适用是同一个道理。拿空串打分会把 plan
全拦掉、回落到 `matchText` 则是尺度混用，两条都不行。

**但「不适用」在混合 scope 里等于「让位」，这点要说清。** 只有 top-k **全是** plan 时
才按 ③ 的名次取 top-1；只要里面还有一条 answer，胜出者就在 answer 里挑 —— 一条
plan 即使 ③ 排第一也拿不到这一次复用。没有第四种选择：让 plan 拿余弦去跟 answer 的
精排分排同一张榜，就是上一段拒绝的尺度混用换个地方混。所以取舍是「answer 优先」，
代价写在 ④ 的 trace 里（`另有 N 条 plan 条目本闸不适用、已让位给 answer`）——
**同一个 scope 里两种载荷混着放，plan 会被 answer 饿死**，用得着 plan 就给它单独的 scope。

### 3. 回答向量与检索片段必须在同一个向量空间

库自己负责所有 embedding，调用方不传向量 —— 就是为了防止这件事。
答案一律用 `RetrievalEncoder.embedPassage` 编码，才能和检索片段比。
用句对模型编码答案、用检索模型编码片段，算出来的余弦没有任何意义
（这个 bug 我自己犯过，`cosine()` 的维度检查就是那次加的）。

### 4. `recallLimit` 必须大于 1

只召回 1 条时精排没有候选可排，④ 退化成二元判断 ——
此时任何关于「精排值不值」的度量都不成立。构造时直接抛错。

### 5. 「该不该缓存」判在闸之前，而且读写分开

六道闸问的都是「这条缓存**还**成不成立」。但有一类问题是**从来就不该被写进去**的 ——
「那第二个呢」（离开这次对话 `matchText` 本身就不完整）、「帮我提交作业」（是动作不是问答）。
交给闸去拦有两个问题：要走完召回+检索+支撑度才发现不该用，付了全部成本什么也没省；
而且它**拦不住写入**，下一次同样的问题就是一次假命中。

所以 `CachePolicy` 在闸 ① 之前，而且是**两个正交开关**而不是一个布尔：

| `noCache` | `noStore` | 行为 | 场景 |
|---|---|---|---|
| — | — | 查、命中就复用；没命中就生成并存 | 绝大多数问题 |
| ✓ | ✓ | 不查、生成、不存 | 「那第二个呢」 |
| ✓ | — | 不查、强制生成、**写回替换旧的** | 「重新回答」 |
| — | ✓ | 照常查，没命中就生成但不存 | 「出五道练习题」 |

第三行是一个布尔表达不出来的：学生嫌答案简略点了「重新回答」，**必须**跳过查询
（不然原样再吐一遍），但新答案该写回去替换旧的 —— 一个学生的一次不满意变成对后面
所有人的改进。不写回的话，每个点重来的学生都各付一次生成，而每次算出的更好答案
全被丢掉 —— 和 `refine` 那条中带逻辑犯的是同一个错。

三条固化在类型里的规矩：

- **`noStore` 生效时写入的三条路都堵死**：`prepareWrite()` / `prepareTicket()` 拒发票据，
  `writeMany()` 对**没带票据**的条目再查一次策略。三条缺一条守卫就只是建议 ——
  `prepareTicket` 是「不走 lookup 直接要票」的后门，而 `WriteOptions.ticket` 本身可选，
  `write(prompt, payload)` 是另一扇正门。带票据的不重查：发票时已经查过了。
- **理由必填**，而且原样出现在 `LookupResult.noCacheReason` / `noStoreReason` 上。
  和 `calibratedOn` 是同一条规矩：一个静默生效的策略，半年后没人知道某类问题
  为什么从来不命中。
- **`Outcome` 里 `bypassed` 单独成一档**，配 `MetricsSnapshot.bypassedByReason`。
  并进 `generated` 的话，一次策略绕开和一次「查了但没命中」在看板上完全一样，
  于是「上游某个信号一直是开的」只表现为命中率下降，查不出原因。

还有一层比按请求信号更粗的闸：**调用类型白名单**（`allowedCallTypes`，默认只含
`completion` / `responses` / `anthropic_messages`）。判据是**输出是不是输入的确定
函数** —— `embedding` 同文本必然同向量、`transcription` 同文件必然同转写，拿相似度
去匹配它们等于用「差不多的输入」换「差不多的输出」，正好摧毁那个输出的意义。
**被排除不等于不该缓存**：那几类走精确缓存是零假命中、命中即赚的一档，只是不该走
这一层。用白名单是因为漏配的方向不同 —— 漏一个新类型只是少几次命中，而漏进一个
不该语义匹配的类型是错答案。

信号从 `prompt.context` 读，和 `ScopeResolver` 共用按请求的通道。**默认实现不内置
任何关键词** —— 「现在/今天/最新」那类词表是最脆的一档，漏一条就是持续的错答案，
中英文还各要维护一份。要用词表或分类器，写一个 `CachePolicy` 用 `combinePolicies`
串上去。

### 6. 标定探针从上传的资料自动生成

手写探针在产品里不成立：验证台的 `RERANK_PROBES` 是照着一门课手写的，而真实场景里
老师传什么、学生问什么都事先不知道。没有探针就没有标定，`calibratedOn` 就是空话。

可做的只有一件：**资料上传的那一刻语料就在手上了。**`generateProbes()` 从中构造
按难度分档的探针，不需要等任何学生流量：

- `identical` 正例 · 逐字相同 —— 天花板检查，这一档都分不出说明模型或 pooling 配错了
- `paraphrase` 正例 · 同一概念的不同问法
- `sibling` 负例 · **同一单元内**的不同概念 —— 难负例，教学场景假命中的主要来源
- `distant` 负例 · 跨单元 —— 容易负例

分档不是装饰：`L1 正则化` 与 `L2 正则化` 词汇几乎全重叠、意思不同，双编码器本来就
分不开；跨单元的对子容易得多。混在一起算总 margin 会被容易那批撑得虚宽，把真正
会造成假命中的那一档盖掉。

两条和别处一致的规矩：**没有改写来源时不造正例**（模板造的「不同问法」字面上几乎
相同，任何编码器都能过，margin 是假的宽），**取样按内容哈希稳定排序**（同一批资料
跑两次必须得到同一组探针，否则 `calibratedOn` 那句话没有意义）。

## 并发

这个库的正常用法是被一个 web backend 并发调用，所以并发下的行为是契约的一部分，
不是实现细节。

**不会坏数据。** `createSemanticCache` 里的可变状态只有 id 计数器和合流表，
JS 单线程，没有数据竞争。

**同一个问题的并发请求只走一次完整流程**（进程内合流，默认开）。合流键里带
`retrievalText` —— 匿名化之后两个学生的 `matchText` 会相同而实体不同，只按
matchText 合流等于亲手制造占位符塌陷。合流的请求共享第一个请求的 `generate`
与 `writeOptions`。

### 三处仍然存在的竞态，以及为什么这样取舍

**① 跨进程并发未命中 → 极少数情况下仍有重复条目。** 合流是进程内的，跨进程挡不住：
两个进程同时未命中同一个问题，会各自生成、各自写入。

`write()` 在落库前查一次「同一个问题是否已经有条目」，有就在写完新的之后把旧的收掉。
这把重复窗口从**整个生成时长**（秒级）缩到**一次往返**（毫秒级）—— 而两次生成
几乎不会在同一毫秒结束。实测：生成 30ms / 90ms 错开完成时只留一条；生成零耗时、
两边在同一个微任务里穿插时仍会留两条。**这是缓解，不是保证。**

查重**比原文，不只比哈希**：`matchHash` 是非密码学哈希，一次碰撞是两个完全不同的
问题，它们该共存不该互相覆盖 —— 和 ② 在读路径上的做法是同一条规矩。

漏过去的那些重复是良性的：

- **浪费，不是错误**：那次生成在写入之前就已经付掉了 —— 查重省的是一行，不是一次生成。
- `getByHash` 的契约规定「多条时返回最新的」（`createdAt` 最大，同毫秒取 id 最大），
  所以读到的是确定的那一条，不会因存储后端不同而不同。
- 多余的行由 TTL 与 `purgeExpired()` 收掉。
- **不加分布式锁**：为省几次生成引入 pg advisory lock 或 Redis 锁，故障面比省下的开销大。

**② 替换条目是「先写后删」，不是「先删后写」。** 中带微调和中带重生成都走
`replaceEntry`：新条目写成功之后才驱逐旧的。所以窗口里存在的是**两条，而不是零条** ——
宁可让并发读者看到一条稍旧的，也不要让它看到未命中然后又生成一条。
写失败时旧条目还在，比丢掉更好。

**③ 一个请求正在驱逐条目 E，另一个刚把 E 召回。** 后者可能返回一条刚被 ⑤ 或 ⑥
判定失效的答案。影响有限：那是「上一毫秒还在用」的答案，且下一次请求就会重新判定。
要彻底消掉需要行级锁，代价不值。

### 组织 id 必填，且 scope 由库拼

`ScopeDecision` 是 `{ key, shared, org }`，三个字段都必填 —— 先前 `org` 不存在，
`key` 还可以直接返回一个字符串。改掉是因为 **③ 是 scope 内的召回**：问题文本不在
key 里，分桶就只靠这个字符串，它错了不是少一次命中，是**跨租户返回别人的答案**，
而且完全静默（向量照样算得出来、相似度照样很高、trace 上一切正常）。

自己拼字符串有两类错法都不报错：**漏了租户**（两个组织都可以有一门 `ml101`）；
**分隔符撞了**（`${org}:${key}` 下 `("a","b:c")` 和 `("a:b","c")` 拼出来一模一样，
一个组织 id 里带冒号就能读到另一个组织的桶）。所以拼接交给 `composeScope()`，
转义后一一对应。单租户部署也要给一个固定值，让它是个显式的决定而不是遗漏。

### 对存储实现的两条硬要求

写自己的 `CacheStore` 时，这两条不能省，否则同一个 bug 在不同后端会有不同症状：

- **`put` 遇到 id 重复必须抛错。** 不能静默丢弃（条目凭空消失），更不能覆盖
  （一个进程改写另一个进程内容完全不同的条目）。id 由库生成，重复只可能是生成器碰撞。
- **`getByHash` 必须确定性地返回最新那条。** 先前内存实现用 `find()`（取先插入的），
  而 pgvector 用 `ORDER BY created_at DESC`（取最新的）—— 一旦并发造出重复，
  换个后端 ② 命中的就是不同的答案。`lab/scripts/storeConformance.ts` 把这两条写成了判据。

### 契约不等于校验：③ 拿回候选后复核 scope

上面那两条是**契约**。但 ② 早就用另一条规矩防住了自己 —— 哈希命中之后再比一次原文，
理由是「`matchHash` 是非密码学哈希，一次碰撞就会返回一条完全无关的答案」。③ 先前
没有对应的动作，而它的失效后果严重得多：pgvector 或 Redis 那侧一个 filter 写错，
就是跨 scope 返回另一门课、另一个组织的答案。

所以 `searchNearest` 返回之后会逐条复核 `entry.scope === scope`，不符的丢掉。
条目已经在手里，只多一次字符串比较，没有额外往返。

**丢弃而不是抛** —— 读路径上一条脏数据不该让整个请求失败（和「缺证据不是有罪」是
同一族取舍）。但丢了多少条会如实写进 ③ 的 trace：`⚠ 丢弃 N 条 scope 不符的候选`。
**这个数不是 0 就意味着存储实现违反了硬要求**，是必须被人看见的缺陷，不是可容忍的常态。

（这一条是读 litellm 的 `RedisSemanticCache._cache_hit_matches_key` 时补的 —— 它同样
不信任自己传给索引的 filter，命中之后再比一次 tag。）

### 没有做的：`(scope, match_hash)` 唯一索引

看起来是根治方案：唯一索引 + upsert，重复条目从源头消失。三个理由没做：

1. **它省的是一行，不是一次生成。** 并发的两个进程在写入之前 LLM 都已经调过了，
   唯一索引只是让第二次写入覆盖第一次。真正贵的那笔钱早就花了。
2. **碰撞时退化更差。** 两个不同问题哈希相同：A 写 → B 覆盖 → ② 比原文不符判未命中
   → A 又覆盖 B → **那一对问题永久互相踢，谁都缓存不上**。不加唯一索引时它们共存，
   ② 取最新那条比原文，另一条仍能被 ③ 召回 —— 优雅降级。
   （实测 300 万条随机串 0 碰撞，所以这是低概率事件；但退化形态的差别是确定的。）
3. **它和「先写后删」直接冲突。** `replaceEntry` 写新条目时会有一瞬间存在两行同键，
   唯一索引下这一步直接失败。要么改回「先删后写」（把并发窗口请回来），
   要么改成原地 UPDATE —— 后者还得再改一次 `entryId` 的语义。

真要数学保证（多租户共用一张表、单 scope 上百万条），该做的是另加一列强哈希
（归一化文本的 SHA-256）作唯一键，而那时要重新想的是整个 key 设计，不只是加一列。

## 诚实的边界

- ⑥ 用的是 bi-encoder 余弦，测的是「同主题」而非「仍成立」。它抓得住实体塌陷
  （检索结果整体换了一批），抓不住细粒度的过期 —— 那是 ⑤ 的活，别指望 ⑥ 兜底。
- **④ 用任务错配的重排器时是负收益，不是"效果差一点"。**实测 13 条用例：
  开与关假命中同为 0，复用 3（开）vs 5（关) —— 零精度提升，砍掉 2 次合法复用。
  探针层面它确实把不可分（−0.2936）变成勉强可分（+0.0344），但那是
  `ms-marco` 在"完全无关"那种容易负例上的功劳；近义反义只差 0.0344。
  **换句对相似度训练的模型会怎样，仍然没有验证过** —— 这条技术栈上拿不到那类模型
  （Quora/STS-B 系列全都没有 ONNX 转换）。已经验证的是另一条路：让手上这个
  query→passage 重排器改比**问↔答**：留一交叉验证从 50%（等于抛硬币）降到 27.8%，
  假负归零。**但同一份数据定不出 floor 的位置**（平台宽 0.62），所以这条支持的是
  「形态选 answer」，不是「floor 用 0.35」。
  加这一层之前，先用 `checkReranker` 证明它在你的数据上拉得开分 ——
  **自检探针必须和 `target` 同形态**，否则算出来的 margin 是另一个尺度上的数。
- **④ 和 ⑥ 在中文上都是「中位好看、尾部重叠」。**问↔答形态下 ④ 剩的 4 个假正里，
  有 2 个是**同篇**近义对（`L1／L2`、`精确率／召回率`）—— candidate 是同一段文本，
  必然同分。这一类 ⑤⑥ 也够不着（同篇 → 版本一致、支撑度也高），
  是六道闸都管不了的那一族，只能靠语料切分或把判据下沉到答案文本。
- 当前测得的 ⑥ 贡献被**坏掉的 ④ 夸大**了 —— ④ 失效时 ⑥ 在替召回层兜底。
  换上任务匹配的精排模型后，⑥ 的边际贡献预计明显变小。
- 上面这一条现在有两个缓解出口（都不是修复）：`Metrics` 的支撑度分布
  （`headroomP10` / `midBandRate`，回答「离翻车多远」，比命中率更早报警），
  以及 `shadow: true` 影子模式（闸全跑、从不复用、读路径严格只读 —— 在真实流量上
  验证判定，且不让未验证的判据毁掉证据）。**「只读」要连写路径一起管**：⑤⑥ 判负后
  尾巴照常生成、照常写入，而 `writeMany` 的去重会把同 `(scope, matchHash)` 的旧条目
  当 duplicate 驱逐 —— 从写路径把承诺打穿。所以影子模式下 `exitedAt` 是 5/6 的那两条
  也跳过写入，只有撞不上去重的真未命中才写。
- **⑥ 判负是破坏性的，而它的输入只有 top-1 —— 检索排序一抖动，判定就换一档。**
  检索侧第一名和第二名只差 0.001 的时候，同一条缓存可能这次被驱逐、下次好好的。
  这和「缺证据不是有罪」那条修正是同一族问题的另一半：现在的语义是「top-1 换了一篇
  就是有罪」。两条可能的收法 ——「低于 `low` 不复用，但要低于 `low − δ` 才驱逐」，
  或者「连续两次判负才删」。**都没有实现**：前者要多标一个 δ、后者要给条目记状态，
  而这两样都得在真实数据上量过再定，不该由库替你决定。眼下的缓解办法是把 `low`
  标得保守一点（离「该复用」那一组的下界远一些），代价是多几次重生成。
- **策略信号走 `prompt.context`，是个字符串字典，拼错不报错。**`needsHistory` 写成
  `needHistory` 策略就静默失效，而且**失效方向是「照常缓存」** —— 最危险的那个方向。
  这和这个库别处的做法是反的（`Calibrated<>` 让你换一个就拿不到旧的、`calibratedOn`
  强制必填）。更一致的做法是让信号类型化（`lookup(prompt, signals)`），眼下没做。
- **缓存身份不含生成端。**`matchHash` 只建在 `matchText` 上，所以换了生成模型、
  换了 temperature，旧答案照样命中。这和「θa 属于生成端，换生成端必须重标」是
  有张力的：判定标准认生成端，缓存身份却不认。**正确的收法不是把模型塞进 key**
  （那会按模型把缓存切碎，跨模型复用是这个场景想要的），而是让条目记下写入方
  （`CacheEntry.meta` 已经能记），⑥ 按条目自己的作者选 θa —— 尚未实现。
- 语义缓存是概率型缓存。零风险的省钱手段（provider prompt caching、精确缓存、
  头部问题策展）该先吃满，它排在这些之后。
